# 芋道本地验收环境

在需要运行的源码目录执行：

```bash
./local                 # 环境1，默认
./local --env 2          # 环境2
```

| 环境 | 浏览器入口 | Compose项目 |
| --- | --- | --- |
| 环境1 | **http://localhost:40001** | `woa-yudao-env1` |
| 环境2 | **http://localhost:40002** | `woa-yudao-env2` |

每套环境包含助手、芋道后端、nginx、MySQL和Redis，网络、数据库卷、会话与费用账本分别独立。只向宿主机发布浏览器入口，容器内地址和端口保持相同。前端使用同源相对地址，由各环境入口将业务请求送入本环境的准入代理。

## 日常命令

| 命令 | 用途 |
| --- | --- |
| `./local` | 启动或更新环境1，无变化且健康时复用 |
| `./local --env 2` | 启动或更新环境2 |
| `./local --env 2 restart` | 重启环境2助手，重新读取模型配置 |
| `./local --env 2 status` | 核验环境2业务接口、助手、源码和实际Runtime |
| `./local --env 2 check` | 只读预检，不创建状态目录、不启动服务、不调用模型 |
| `./local --env 2 logs` | 环境2助手最近80行日志 |
| `./local --env 2 logs app` | 环境2基础服务最近80行日志 |
| `./local --env 2 stop` | 停止环境2助手，保留业务服务和数据 |

省略`--env`始终选择环境1；不会记忆上次选择或自动换到空闲环境。诊断和修复命令应始终携带当前任务选定的环境编号。

`local`按脚本自身所在位置定位源码，不依赖执行时的工作目录、Git分支或worktree类型。容器只读挂载该目录的源码、策略和构建产物；不挂载`.env`、内部研究材料、宿主机虚拟环境或前端依赖。普通checkout、worktree和独立clone使用相同入口。同一源码目录启动两套环境时共享代码；两个需求并行修改代码时使用两个独立目录。

运行中的环境记录所属源码目录，其他目录不能自动接管或停止它。切换目录时先从原目录停止该环境助手，再在新目录用相同编号启动；数据库与助手持久状态保留。两个环境的命令锁独立，同一源码目录的前端构建串行。

普通Python修改只重启所选助手，前端输入变化才构建；构建失败保留原助手。依赖镜像按`requirements.lock`和Dockerfile内容缓存，普通源码变化不重建镜像；依赖变化才构建镜像。模型`.env`变化会重新创建所选助手容器以应用配置。业务服务不随助手代码更新重启，也不启用保存文件自动重启。

## 首次准备

1. 按根目录README准备Python 3.12的`.venv`并安装依赖与芋道适配器：`.venv/bin/python -m pip install --no-deps --editable examples/yudao`。
2. 安装Node.js、npm、Docker Engine及Docker Compose 2.30或更新版本。Docker Desktop需处于运行状态。
3. 按[芋道构建说明](../../examples/yudao/deploy/README.md#build-and-run)准备当前源码目录的固定缓存`.q0-cache/yudao/`：带Java补丁的JAR、管理前端`ui/dist-prod/`、初始化SQL及上游源码。管理前端的`VITE_BASE_URL`保持空值，不能写死旧地址。页面控制器见[部署指南](deploy-yudao.md#固定缓存)。
4. 在当前目录Git忽略的`.env`填写`AGENT_OPENAI_BASE_URL`、`AGENT_OPENAI_API_KEY`、`AGENT_OPENAI_MODEL`及可选`AGENT_PROVIDER`，模型须有已登记价格。仅必要模型配置以私有文件注入容器，不进入镜像。模型地址若指向宿主机回环地址，启动器仅在容器配置中转换为`host.docker.internal`，原`.env`不改。
5. 执行`./local check`后执行`./local`；环境2用对应的`--env 2`命令。首次需要构建依赖镜像。

实例配置和运行状态位于`$XDG_STATE_HOME/web-operation-agent/yudao/env1/`与`env2/`；未设置`XDG_STATE_HOME`时使用`~/.local/state/web-operation-agent/yudao/`。同一用户的源码目录共用这两个固定实例，目录包含数据库配置`application.env`、必要模型配置`agent.env`、源码挂载配置及`state/`。这些私有文件不进入Git；已有数据卷但原数据库配置缺失时拒绝启动，不生成替代密码或重置数据。

首次创建新卷按缓存SQL建立表结构和初始系统数据，不自动补充业务样本。迁移已有本地合成数据时，备份和导入新卷是独立的一次性准备：两套新卷各自导入，旧卷保留，登录令牌和Redis不沿用，助手会话与账本重新建立。日常启动不备份、恢复、seed或迁移数据库。人工登录账号可保存在所选实例的`account.json`中，启动器不读取或自动登录它。

`.q0-cache/yudao`仍是当前源码目录的基础缓存；`.q0-cache/yudao-local/compose-build.json`仅记录前端构建。原目录下的旧账号、会话、账本与日志保留，不作为新实例运行状态使用。

## 旧环境过渡

旧Compose项目更名为`woa-yudao-local-deprecated`，继续使用原数据库卷；旧宿主机助手入口`http://localhost:48163`保留。新入口不会停止旧助手、接管旧端口或删除旧卷。原`local.local.toml`和`local.example.toml`只供旧启动器采用旧项目，新双实例入口不读取它们。

旧项目的原配置保存在本机`.q0-cache/yudao-local/deprecated-compose/compose.json`。它包含私有环境配置，不提交或输出；启动或重建旧项目时使用这份配置，避免旧启动器按更名后的默认卷名创建空库。旧业务栈就绪后，旧启动器可复用它。旧服务原本停止时，更名不自动启动它；浏览器访问已有旧入口不要求先合并迁移提交。

## 扩充合成验收数据

需要验证分页和较长列表时，可显式运行部署目录的扩充脚本。显式指定所选环境的地址、账号与备份；下例使用环境1和默认状态目录。它只接受本机回环地址、已有 MySQL 压缩备份和 `--apply`，不由 `./local` 自动触发。先在没有验收回合执行的窗口备份当前实例，再运行：

```bash
.venv/bin/python examples/yudao/deploy/seed_scale.py \
  --base http://localhost:40001 \
  --account ~/.local/state/web-operation-agent/yudao/env1/account.json \
  --backup .q0-cache/yudao/snapshots/before-scale.sql.gz \
  --report ~/.local/state/web-operation-agent/yudao/env1/scale-report.json --apply
```

默认每个主要实体新增 120 条具名合成记录，覆盖系统用户、岗位、部门、通知、HRM 员工、CRM 客户／联系人／线索／产品／商机／草稿合同、ERP 基础资料／采购与销售订单／已审核采购入库、WMS 商品规格、MES 客户与供应商、PMS 项目。数据包含不同日期、状态、金额和关联明细。采购入库产生应用自己的库存记录；不提交支付、邮件或外部通知。新增用户使用随机密码且不授予角色。

脚本通过应用接口新增，以完整分页中的确切键识别已有记录；失败即停止，不自动重试不确定的提交。再次执行前先核对失败步骤在应用里的状态。报告由重新读取的全量列表产生。扩充会改变全量数量、合计和排名，旧快照及其金标必须保留；后续验收使用新数据版本重新核对的金标，不能把前后结果混作同一基线。

## 显式准备跨模块演示数据

`examples/yudao/deploy/demo_data.py` 提供独立的合成演示数据准备工具，不由 `./local` 自动运行。执行前必须释放所有冻结测评占用，保存并演练恢复完整数据库备份；旧题、答案和成绩继续绑定原数据，不能移植到新数据。

工具只接受回环地址、已有MySQL压缩备份和 `--apply`。`menus` 删除三个上游外链、禁用未服务模块，并建立只读探索角色及 `demoexplorer` 账号；开发运维、接入示例和AI/支付/公众号/IM菜单不授予该角色，管理员入口保留。`broad` 经应用接口准备常用模块样本，`large --size N` 扩充指定CRM和ERP集合，最高5,000个主记录；先小批验证再逐级扩量。`personal` 使用临时的最小准备权限为探索账号建立日程、计划和汇报，结束时收回权限；`ownership` 通过应用正式转移接口设置新增客户及联系人的负责人，不能仅凭创建参数判断归属。财务凭证准备需要先在隔离合成实例中初始化科目表。参数见 `--help`；各分组名称定义在部署目录的 `demo_data_profiles.py`、`demo_data_extended.py`、`demo_data_flows.py` 和 `demo_data_coverage.py`。账号凭据只写入指定状态目录的上级 `demo-account.json`，不要提交或粘贴到日志。

按页面覆盖补数时，`broad --groups coverage-... --size 5` 可选择额外设备、仓储与质检草稿、模板和常用配置分组；这些分组通常各准备5条，签到规则固定7天。`coverage-personal --size 5` 以临时最小权限建立探索账号自己的办公申请草稿、线索、联系人、商机和合同草稿，结束时撤销授权。申请不提交审批，仓储单据不执行库存变更。页面覆盖率须固定账号和可见菜单清单，以实际页面显示记录核验；卡片/配置表单、空页、异常页和隐藏菜单分别列明，不能把辅助下拉列表的数据当成主页面有数据。管理员还保留额外运维菜单，且个人页面按当前身份显示，不能把探索账号的覆盖率推广到所有账号。

每次写入有不含请求正文的回执日志；发生未知结果或未确认派发时工具拒绝继续，须先人工核对。应用拒绝的独立分组保留失败，不能自动重试或算作成功；未提供服务或依赖未贯通的页面须单列。以应用分页读回、关联与金额核对及实际页面为验收依据，不能将预定数量或数据库行数当作可用性证据。`verify_demo_data.py` 以探索账号完整分页核对数量、关联、订单金额和借贷平衡；`verify_demo_browser.py` 在全新浏览器会话抽查六个核心列表。这些检查不证明所有菜单、完整业务闭环或模型问答已通过。新数据冻结后登记快照、版本、账号权限、数量和摘要。日常 `./deploy` 不同步数据库，服务器数据替换须独立备份、演练并核对两端业务基线，默认不复制本地凭据和会话；所有者明确授权连同账号全量替换时，账号随快照迁移，替换后仍须作废跨环境会话。

## 地址、权限和费用

所有对外监听绑定本机回环地址。浏览器始终使用所选环境的`localhost:40001`或`localhost:40002`；旧IP形式的HTML请求会跳转至对应规范地址。同一浏览器可以同时访问两套环境，登录存储和准入窗口按各自来源隔离。

模型按当前登录账号读取。新本地宿主关闭类型化写入和编辑预填，页面能力沿应用准入策略执行，提交仍由用户手动完成。每环境每账号日限额为¥20，费用记录在所选实例的`state/`，不沿用旧账本。

入口安装仓库附带、与当前缓存逐字段核验的金额策略；预检核对发布版本、源码摘要和单位换算，不匹配时拒绝启动。只有策略列明的接口字段可直接按页面单位做程序汇总，其余金额仍需同记录页面核对。此设置不改变云部署策略。

健康检查分别核对业务成功响应、助手就绪状态、环境编号、源码目录及实际Runtime。页面200或端口监听不足以通过。检查不调用模型，不证明自然语言题目的成功率、调用数或耗时；完整用户验收需登录后逐题进行。

## 按错误处理

| 现象 | 下一步，以环境2为例 |
| --- | --- |
| 工具、模型配置、价格或缓存缺失 | `./local --env 2 check`，只补明确缺项 |
| 基础应用未就绪 | `./local --env 2 logs app`，不循环重建或恢复数据库 |
| 助手不可用 | `./local --env 2 status`后查看`logs`，修正后`restart` |
| 源码或Runtime不一致 | `./local --env 2`，构建必要资源并更新助手 |
| 环境由其他源码目录运行 | 先从原目录停止该环境，再从当前目录启动；不接管对方 |
| 对外端口被占用 | 识别服务归属，不杀未知进程或自动更换环境 |
| 数据库配置缺失但数据卷已存在 | 恢复所选实例的原`application.env`，不重置密码或数据 |
| 登录后401 | 在对应环境入口重新登录，保留实际认证错误 |

业务服务启动最多等五分钟，助手最多等45秒；超时以非零退出码结束，日志保留，不盲目重试。助手重启可能中断当前回合，在验收题之间执行。退出终端后容器继续运行，机器或Docker重启后再次执行对应`./local`命令。
