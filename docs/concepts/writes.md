# 写入模型

写入是这个系统里唯一能让业务数据变化的事，因此它的边界比读取严得多。核心规则一句话：**每项变更绑定一次完整可见的批准，只派发一次，由应用在同一 actor 下核验结果；不确定的写入绝不重试。**

## 谁有权要求写入

只有**用户本人的请求**能要求写入。范围提示、工具可用性、Skill 正文、记录与页面里的文字都不能。Skill 任务声明从完整请求解释执行意图，解释可能出错（包括把否定读成执行），所以每项写入仍需一次完整可见的审批卡片。

## 共享写链路

两种执行器、以及模型驱动回合里的 Skill 写入，都走同一段链路（`BusinessWriteService`）：

```text
提案（只有已加载 Skill 支撑的操作）
  → 只读准备（当前 actor 下解析目标、读必要原值、构造原生请求）
  → 效果投影与锁定请求核对
  → 完整可见审批卡片
  → 新的一次性批准
  → 派发前复查（取消状态、权限、冲突）
  → 至多派发一次
  → 同 actor 回读核验，逐项回执
  → verified / refused / cancelled / indeterminate
```

- **效果投影**：应用从实际准备好的原生请求解码出语义变更（目标、全部变化、保留输入、默认与派生值、连带效果），参与审批摘要。改它就令该批准失效。
- **一次批准**：绑定规范化提案摘要、效果、目标、principal、turn 与 operation，只能消费一次。
- **单次派发**：journal 原子地把提案从 `prepared` 认领为 `dispatching`；并发调用与进程重启都不能再次执行同一提案。同一业务键上已有的 `dispatching`/`indeterminate` 提案会阻止第二个并发提案通过。
- **回读核验**：派发后由应用产生逐项回执；必需回执齐全才记为完成。已确认但不完整的结果保持 `indeterminate`，保留对账证据，且不能自动重放。

## 三种结果，三种处理

| 结果 | 含义 | 之后怎么办 |
| --- | --- | --- |
| `completed` | 应用核验的效果覆盖了全部必需项 | 答复里写明办了什么；本回合要求的其它事接着做，每件写入各自批准 |
| `not_approved` / 派发时被拒 | 用户没批准，或应用在执行时明确拒绝 | 结束本回合，不再重发 |
| `indeterminate` | 派发过，但结果无法证明（超时、断连、回读失败） | 结束本回合，不自动重试；由应用只读核对或人工裁决 |

**只有应用能保证“被拒的调用没有产生业务变更”时**，才允许把失败报成权限类错误；仍可能部分完成或结果未知时必须按 `indeterminate` 处理。

应用若能把不确定响应绑定到确切目标，可在同一 actor 下做一次只读对账。读到全部批准效果可以升级为完成；未读到不能证明先前请求已经停止，仍保留不确定状态和 journal 阻挡。芋道的已知 ID 更新及部分状态变更使用这条规则；没有可归属 ID 的创建错误保持不确定。

芋道原生写入逐项记录了后端服务方法及其事务声明。只有明确来自 Spring MVC 参数绑定、在进入控制器前产生的错误，才按“未生效”处理。相似的参数校验文字也可能来自服务执行中，因此不能仅凭错误码 400、事务声明或一次未找到记录的回读判定回滚。服务错误和传输错误保持不确定；对已知目标的完整同账号回读只能把结果升级为完成。

芋道跟进创建不是事务性的复合写入。派发前会按同一账号读取目标的 CRM 权限：不是 CRM 管理员且该目标完全没有权限记录时，在审批前拒绝，并在派发前复查。非空权限记录仍不能代替应用自己的写权限判断；如果应用在派发后报错且无法证明全部效果，结果仍保持不确定。

芋道按本轮原话决定是否隐藏 Skill 写入工具。“我来提交”“自己保存”以及明确要求在编辑表单内改值而未要求保存，表示把提交留给用户；“我提交的申请”和作为筛选条件的“草稿状态”只是查询描述，不算草稿意图。明确要求在表单内改完后保存时仍保留写入工具。词表未命中的说法仍由模型判断，任何真实写入都要经过独立审批。

## 原生表单与行内按钮：批准后由程序点一次

没有 Skill 的新增、修改和行内状态动作（审核、启停、关闭等），应用可以声明“批准后提交”。模型只请求提交；程序做其余的事：

1. 读取原生表单组件绑定的**整份表单数据**（含隐藏字段、关联对象编号、明细行），表单在弹窗或整页中都按同一机制读取，载入时一份、请求提交时一份；读不出来、含密码类字段、应用校验未通过的，不出卡，把填好的表单留给用户。
2. 逐个核对助手本轮填写或选择的值：必须来自用户原话（日期、时间、金额按含义比较）、用户选定的真实候选，或针对该字段的换算回执；否则不出卡，改为向用户确认这个值。
3. 修改以同账号读取的记录现值为准。页面打开时自行改值的字段先还原，并重新做应用校验；还原失败或页面又改回的，留给用户核对。批准卡列出目标、全部差异、默认或联动变化、已还原的打开时变化，以及将要点的按钮。行内按钮只使用目标表格唯一对应的已观察列表接口认定实体，绑定不明时不出卡。
4. 批准后程序重读表单和同账号的目标记录，任一与批准时不同就不点；否则在许可内点击一次提交控件。许可只放行卡上那一次效果：路径属于目标实体的已登记写接口，记录编号等于卡上的目标，请求体与提交时的表单数据一致，改动的字段正好是卡上的变化；同一批准下相同的请求只放行第一个，放行前守卫再读一次目标记录，有变化就拦下。
5. 应用自己弹出的确认框：只确认同一动作的，程序点确定；出现卡上没有的后果（不可逆、删除、连带清理）的，点取消。
6. 回读按同账号读目标记录，核对要求的字段；终态为完成、部分完成、未执行、失败或结果不明，写明哪些已生效，不重试。

删除、作废、关闭等危险动作要先在对话里说明影响并取得用户明确确认，之后才出卡。用户自己的操作不带助手标记，不受许可约束。

已知限制：放行前重读之后、应用处理之前的几十毫秒，别人在同一条记录上的保存可能被覆盖，与用户自己点保存相同；密码和文件上传留给用户；无法唯一识别的表单或表格也交给用户。默认记录摘要与卡片内容，整份表单、请求和基线记录仅在集成明确接入的本地私有证据采集中保留。

## 页面的“同意”不是写入批准

页面操作需要用户同意，但它是**每段对话一次**的页面操作许可，不是写入批准：它不进入写入见证、不计入审批。业务变更仍逐条在自己的卡片上确认。

若应用为准备好的确切写入提案声明了可核验的暂存表单，写入卡还可提供“只填到表单，我自己提交”。用户选择它时，该卡同时给本次表单交接所需的页面操作许可；服务端消费卡片、撤下本轮写入工具，并由应用适配器按卡片绑定的目标和值打开及填写表单。每一步仍受页面动作准入和回执核验；最终只标出提交按钮。业务写入不会派发；交接不确定时停止并说明页面可能已有未保存的输入。未声明转换的操作仍只有批准或取消。当前真实浏览器验证覆盖合成 Contacts 的新建联系人表单，芋道原生写入尚未接入此转换。

同理，页面上的点击、填写、选择、提交、跳转和返回在某些应用里都可能触发服务端写入，不能只凭工具名判断安全性；只读路由只约束业务意图与允许到达的位置，不降低这次导航的写入风险。

## 应用侧要做的事

- 提供**持久 mutation journal**、覆盖每个写工具的后置条件 verifier 和核对端口；
- 在准备阶段做只读定位、读必要原值、构造最小请求体（只含批准的变化与接口必填的原值，不回传整条记录）；
- 报告当前匹配记录数与扫描完整性；无法判断时保守返回需人工处理的 unknown；
- 拒绝或授权都要如实分类（权限拒绝、业务拒绝、不确定）。

不确定写入的人工裁决入口见[持久化运维](../guides/operate-durably.md)。
