# 执行器

核心保留目标式与模型驱动两种组合方式，共用身份绑定、本段对话可见的页面操作同意、写入观察、回执和预算。芋道原生宿主只使用应用无关的 `ModelDrivenTurnExecutor`（`slim`）；旧 `goal`、`page-agent` 配置明确拒绝，不自动回退。目标式路径供其它接入使用。

## 目标式执行器

模型对照应用索引**一次性声明**整个请求，服务端确定性地解析每一项声明：

- 记录 → 应用自己的名称搜索
- 字段值 → 类型化读取
- 计数、求和、数值极值 → 限定范围的查询
- 页面 → 已审核路由；页签 → 可见名称；筛选与分组 → 页面自身状态
- 要做的修改 → 把对应控件高亮出来交给用户

答复由解析出的值生成，**不采用模型的文字**，所以回合报告的事实都是它读到的。所有声明项落实后回合才算完成；做不到的部分如实说明；多条记录都符合又无法区分时追问是哪一条；指名的记录不存在时不会改成新建。

逐步解析回路：最新观察 → 模型选一个工具 → 服务端校验（schema、Skill、策略、路由、写权限）→ 执行动作或工具 → 返回结果与**新的页面观察** → 用运行时事实修正计划再进下一轮。页面元素引用只在产生它的 observation epoch 内有效。

声明是模型输出，可能选错实体、字段或范围；这条路径会增加模型调用和时延，不是一次调用的回合。

## 模型驱动回合（芋道唯一执行器 `slim`）

模型在同一段对话里**逐步**从一组固定工具中选择下一步，每个工具结果和新的页面观察都回到同一段对话。不带写入时基础工具集是十五个：`search_menu`、`find_record`、`goto`、`observe`、`click`、`input`、`select`、`fill_fields`、`scroll`、`search_api`、`entity_rules`、`load_domain_guide`、`call_api`、`highlight`、`finish`（其中 `entity_rules` 按部署编译期规则读取拒绝与连带影响，`load_domain_guide` 读取八大业务域的只读消歧与口径说明；行表执行器另带同轮 `tables`、`sql`、`date_range`）。开启写入后另加 `load_skill` 与 `read_skill_resource`，已加载 Skill 的每个写入操作各成为一个带已安装输入 schema 的工具。

芋道在每轮原话上判断草稿与保存意图：明确要求先填的回合隐藏 Skill 写入工具，明确要求保存的回合提示使用已安装的 Skill；未命中词表时不改变工具集。草稿交接后的字段修改仍按草稿处理，除非用户明确要求提交。页面预填工具不受该判断影响，写入仍须逐项批准。

改写数据的事由写入链路承担；只是一句话里同时含查询、页面和写入时，每一类都要做完。

芋道组合只在版本匹配的方法围栏、已审核页面策略、live forms 和应用自己的只读窗口下启动；配置缺失时在模型和网络启动前拒绝，从不按提交控件。默认在会话建立时预热菜单/API 说明及 outline，不预读明细；冷启动测试配置可关闭预热，生产 CLI 不提供该开关。

页面策略按部署版本生成当前测试账号菜单页与已知记录路由的七类动作清单，并绑定同版方法围栏的摘要；可按路由和动作类别排除。查询行的导出、导入、删除等按钮由运行时文字和图标拒绝；入口及暂存行仍要由真实控件位置、只读窗口和新观察核验。未核验的暂存动作在能证明没有持久化效果时交回同一模型继续判断，不计为完成。公共循环按工具、目标、值与错误码收住重复失败，并在六次页面失败后要求总结。

公共循环校验闭合工具 schema，由应用签发并单次消费动作和暂存步骤授权，每个工具结果与新观察回到同一 Agent。应用特有的菜单、接口、日期、分页和明细过程留在 Adapter；结构不同的合成 Contacts REST/HTML 应用验证同一公共循环。

工具可以合并一个经审核的表单阶段：`goto(open=...)` 导航并打开入口；`fill_fields` 可以用 `add_lines` 建暂存行，并以 `then_highlight` 和 `answer` 交接。每个子步骤仍逐个准入和核验，整体回读所填值及未填写保留值后才高亮提交，服务端明确提示人工检查和手动提交。筛选可用 `then_click`，仅在真实查询核验通过后结束；页签和分页也须绑定确切命令的稳定核验结果。

普通模型结束记为 `not_claimed`，局部动作成功不证明整个请求或模型答案正确。可选源码工具也在同一循环，当前业务值与配置必须读应用；源码只回答实现问题，结论绑定本轮引用，引用校验不证明语义正确。具体拒绝、恢复与完成条件见[运行时行为详情](../reference/runtime-behavior.md)。

两个执行器的差别只在“谁决定下一步”：目标式由服务端按声明确定性解析，模型驱动回合由模型逐步选择。**写入路径、审批卡片、审计与预算完全相同。**

## 事实与知识的优先级

知识来源回答的问题不同，不能混成一个“可信度分数”。冲突时，更新且更接近执行点的运行时事实优先：

| 优先级 | 来源 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 1 | 最新页面观察与动作回执 | 当前 URL、DOM、可见控件、动作是否得到 Runtime 回执 | 隐藏记录、数据库提交、未显示的权限 |
| 2 | 同 actor 的业务读取与写后回读 | 当前业务数据、适配器实际回读到的写入结果 | 浏览器当前视觉状态 |
| 3 | 当前 actor 的运行时目录与 Adapter 元数据 | 可发现的实体、页面提示、字段描述、可读操作 | 当前记录、页面默认筛选的真实结果、写授权 |
| 4 | 已审核的 Skill、业务文档 | 工具用途、槽位、只读路由、操作约束 | 当前记录、当前权限、本次动作结果 |
| 5 | 与部署版本绑定的源码与 Git 证据 | 静态声明、可能代码路径、实现片段、提交/所有权 | 当前数据、当前有效权限、某事件的实际原因 |

页面负责 UI 真值，业务接口负责动态业务数据；两者不一致时停止做成功声明，用新的观察或同 actor 回读消除冲突。源码始终是不可信先验，不能授权页面动作或接口调用。

## 上下文按来源职责组装

页面、对话历史、Skill 和部署源码不是一个等价的大文本池，每轮由服务端按职责组装：

- 最新页面观察始终是实时 grounding 基线；
- 只有当前措辞指向历史或正在回答澄清时，才加入有界、已脱敏、明确标为可能陈旧的对话历史（默认最近四回合、总数 32 KiB，其中业务事实 16 KiB）；
- Skill 按当前任务选出有限候选，真正的类型化工具在显式加载后才出现；
- 部署源码只在启用时以惰性查询提供（带 release、file:line 与字节哈希），不整体注入。

任何来源都不能借被选入上下文扩大工具 scope 或写授权。新回合在陈述事实或做页面动作前必须重新读取页面或接口；历史的 `ui_path` 不会进入本轮路由，因此不能授权跳转。
