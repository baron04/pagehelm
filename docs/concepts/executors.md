# 执行器

产品有两种执行器，共用同一套协议与边界：身份绑定、本段对话可见的页面操作同意、写入观察、回执和预算。

## 目标式执行器（默认）

模型对照应用索引**一次性声明**整个请求，服务端确定性地解析每一项声明：

- 记录 → 应用自己的名称搜索
- 字段值 → 类型化读取
- 计数、求和、数值极值 → 限定范围的查询
- 页面 → 已审核路由；页签 → 可见名称；筛选与分组 → 页面自身状态
- 要做的修改 → 把对应控件高亮出来交给用户

答复由解析出的值生成，**不采用模型的文字**，所以回合报告的事实都是它读到的。所有声明项落实后回合才算完成；做不到的部分如实说明；多条记录都符合又无法区分时追问是哪一条；指名的记录不存在时不会改成新建。

逐步解析回路：最新观察 → 模型选一个工具 → 服务端校验（schema、Skill、策略、路由、写权限）→ 执行动作或工具 → 返回结果与**新的页面观察** → 用运行时事实修正计划再进下一轮。页面元素引用只在产生它的 observation epoch 内有效。

声明是模型输出，可能选错实体、字段或范围；这条路径会增加模型调用和时延，不是一次调用的回合。

## 模型驱动回合（`--executor slim`，实验性）

模型在同一段对话里**逐步**从一组固定工具中选择下一步，每个工具结果和新的页面观察都回到同一段对话。不带写入时这组工具是十三个：`search_menu`、`find_record`、`goto`、`observe`、`click`、`input`、`select`、`fill_fields`、`scroll`、`search_api`、`call_api`、`highlight`、`finish`。开启写入后另加 `load_skill` 与 `read_skill_resource`，已加载 Skill 的每个写入操作各成为一个带已安装输入 schema 的工具。

改写数据的事由写入链路承担；只是一句话里同时含查询、页面和写入时，每一类都要做完。

它只在方法围栏加应用自己的只读窗口下启动，从不按提交控件；宣布完成前另一次模型请求对照用户原话、页面真实状态与本轮程序记录复核一遍。

两个执行器的差别只在“谁决定下一步”：目标式由服务端按声明确定性解析，模型驱动回合由模型逐步选择。**写入路径、审批卡片、审计与预算完全相同。**

## 事实与知识的优先级

知识来源回答的问题不同，不能混成一个“可信度分数”。冲突时，更新且更接近执行点的运行时事实优先：

| 优先级 | 来源 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 1 | 最新页面观察与动作回执 | 当前 URL、DOM、可见控件、动作是否得到 Runtime 回执 | 隐藏记录、数据库提交、未显示的权限 |
| 2 | 同 actor 的业务读取与写后回读 | 当前业务数据、适配器实际回读到的写入结果 | 浏览器当前视觉状态 |
| 3 | 当前 actor 的运行时目录与 Adapter 元数据 | 可发现的实体、页面提示、字段描述、可读操作 | 当前记录、页面默认筛选的真实结果、写授权 |
| 4 | 已审核的 Skill、业务文档 | 工具用途、槽位、只读路由、操作约束 | 当前记录、当前权限、本次动作结果 |
| 5 | 与部署版本绑定的源码与 Git 证据 | 静态声明、可能代码路径、实现片段、提交/所有权 | 当前数据、当前有效权限、某事件的实际原因 |

页面负责 UI 真值，业务接口负责动态业务数据；两者不一致时停止做成功声明，用新的观察或同 actor 回读消除冲突。源码始终是不可信先验，不能授权页面动作或接口调用。

## 上下文按来源职责组装

页面、对话历史、Skill 和部署源码不是一个等价的大文本池，每轮由服务端按职责组装：

- 最新页面观察始终是实时 grounding 基线；
- 只有当前措辞指向历史或正在回答澄清时，才加入有界、已脱敏、明确标为可能陈旧的对话历史（默认最近四回合、总数 32 KiB，其中业务事实 16 KiB）；
- Skill 按当前任务选出有限候选，真正的类型化工具在显式加载后才出现；
- 部署源码只在启用时以惰性查询提供（带 release、file:line 与字节哈希），不整体注入。

任何来源都不能借被选入上下文扩大工具 scope 或写授权。新回合在陈述事实或做页面动作前必须重新读取页面或接口；历史的 `ui_path` 不会进入本轮路由，因此不能授权跳转。
