# Odoo product evaluation apparatus (P7.4)

This directory holds the evaluation apparatus for the Odoo reference integration. It is outside `src/`, is not packaged, and product code must never import it. It measures whether a fixed Web Operation Agent composition passes a scoped product screening gate on declared synthetic Odoo 18 workflows, with an exploratory comparison against official PageAgent on single-turn read and navigation tasks. It does not attribute differences to an agent engine and does not support a non-inferiority or "90% success rate" claim.

The apparatus has been qualified without any external model call. No paid batch has been run, so nothing here is a success rate.

## Arms and capabilities

| Arm | Capability | Used for |
| --- | --- | --- |
| `pageagent_browser_only` | Official PageAgentCore 1.12.4 in real Chromium, signed in as the same synthetic Odoo user; built-in DOM tools only; no Skill, business API or assistant (the addon's assertion and assistant endpoints are refused in its browser context). Single-turn, read-only. Its final answer is the `done` action's text, read through the bridge. | Exploratory read/navigation comparison on a preregistered subset |
| `woa_product` | The single-node Odoo deployment: ordinary Odoo login, addon bootstrap, assistant panel, server ReAct turn, product Skill selection and `load_skill`, typed Odoo tools under the actor's delegated API key, approval card, durable journal and same-actor readback. Its answer is what the panel shows by default. | Every supported task and the screening gate |

A PageAgent arm with the product's Skills and typed tools is not built. [`equivalence.py`](equivalence.py) inspects the pinned PageAgentCore distribution and the shipped product and records why the two cannot start from the same Skill catalog without a prompt-reading harness or a modified PageAgentCore. Capabilities are fixed by arm and actor delegation; no runner reads a task's evaluator specification.

The two arms' answers reach the evaluator through different channels. PageAgent does not render its `done` text in the page, so its answer is a value no user sees, while WOA's is the one the panel shows. This does not affect the WOA-only development batches, but no formal PageAgent comparison runs until the channels match or the protocol records the difference and stops claiming one visible-answer rule for both arms.

## Components

- [`population.py`](population.py) generates the synthetic Odoo population from a 128-bit seed. Tasks name record *roles*, so the development and held-out sets share one generator with independently sealed seeds. [`odoo_seed.py`](odoo_seed.py) builds that population inside an isolated, demo-free Odoo database, freezes scheduled actions, issues per-user API keys and verifies every predicted reference, amount, state, date and invoice number before committing.
- [`tasks.py`](tasks.py) validates, seals and instantiates task sets. Each split has 30 families, five per stratum, with a structural fingerprint; families and fingerprints must be disjoint across splits while causal-shape and class distributions match. Instantiation returns a `RunnerInput` (messages, entry path, actor) separate from the `EvaluatorInput`.
- [`tasksets/`](tasksets) holds the public development set, both seals and the split verification. The held-out set and both seeds stay in ignored private storage, with an encrypted escrow outside the repository.
- [`stack.py`](stack.py) and [`compose.p74.yml`](compose.p74.yml) run the isolated `woa-p74-*` Compose project on top of `deploy/odoo-single-node`. The overlay adds only a loopback RPC port for the evaluator and a provider relay inside the Agent's network namespace; the Agent gets a verified-empty state directory and a new provider token before every attempt. Images are built only from a clean checkout and labelled with its full commit. [`revision.py`](revision.py) checks the running Agent image's `org.opencontainers.image.revision` against that clean HEAD, and every batch header and qualification records the verified candidate.
- [`gateway.py`](gateway.py) is the only provider path for both arms. It binds requests to the open attempt, appends `model_request_dispatched` to the attempt ledger before forwarding, records the returned model string and usage afterwards, enforces the shared hard budgets, and records any request that belongs to no attempt. Every dispatch is a lease on the ledger and settles exactly once: an answer, a refusal, or -- once the provider's own request deadline has passed without one -- a `model_response_unresolved` record. An attempt closing on the gateway stops taking new calls, waits for the leases it still holds, and writes down what never settled while it is still open, so the records the driver costs cannot change underneath it and no answer is left for a ledger that would no longer take it. The apparatus adds no drain timeout of its own and keeps nothing beside the ledger; an unresolved call costs the attempt as usage unavailable and goes to the bill reconciliation with the calls the spend ledger could not record, and an answer that arrives afterwards changes nothing. It fails closed on request parameters: a request may carry only the shared chat-completion fields and the model's own option fields, with temperature 0, the product's option values for the requested alias and an integer `max_tokens` from one to the frozen cap. PageAgent's server-held completion client removes `top_p`, `max_completion_tokens` and the pinned bundle's `enable_thinking` patch and adds the options before sending. Input is bounded by request bytes rather than tokens, and every forwarded request's actual parameters are recorded. Behind the gateway sits a scripted backend or `UpstreamBackend`, the dedicated evaluation provider: one POST per request and never a retry, a request id sent as `x-woa-request-id`, and every dispatched call accounted to the spend ledger the way the product's own client accounts it, including an explicit usage-unavailable row. Every provider result is typed, and attempts are classified from the gateway's own records, the same for both arms: an outage, a rate limit, a dropped connection or an answer outside the evaluation provider's response contract (not JSON, or without a model string or usage) is an apparatus fault with the gateway record as its evidence; a refused credential seals the batch, and the next batch needs a later preflight; a call the spend ledger cannot record is an accounting failure that is never replaced, seals the batch and closes the gateway to every later request; an input the provider or the gateway rejects as too long, a deadline and an exhausted call budget are scorable product results; and a request outside the frozen request contract is the product's own failure and seals the batch. Any other gateway record is classification contract drift. Each backend names its provider id, a normalized endpoint digest and a domain-separated credential identity digest; with the requested alias and the request contract, that runtime provider binding is recorded by the preflight and bound by every batch header and attempt, so a changed endpoint or key needs a new preflight. [`provider_relay.py`](provider_relay.py) forwards bytes from the Agent's loopback to the gateway.
- [`ledger.py`](ledger.py) is the append-only, hash-chained attempt ledger. Its header binds the protocol digest, the task-set seal, the fixture manifest and baseline guard, a capability digest for every scheduled arm, the verified candidate, the runtime provider binding and the schedule with the seed a formal schedule was derived from; an attempt must use exactly the fixture, capability and provider binding its batch binds. The link to the previous batch names its purpose, candidate, chain head and ending. In a development chain a new candidate may follow any finished batch, while the same candidate continues only after an exogenous stop -- a model-string change, an exhausted replacement cap, a refused credential or an accounting failure; held-out and qualification chains start again under the same protocol version only after an exogenous stop. It enforces one open attempt, a fixed record order, legal combinations of the three result axes from [`outcomes.py`](outcomes.py), bounded replacements that immediately follow their original, and mandatory seals after safety events, reset failures, unclassified results, model-string changes, unowned requests, exhausted replacement caps, a refused provider credential, an unaccounted call and a request outside the frozen request contract. A WOA reset also carries content-free Agent-state assertions: the verified-empty start, sessions and unresolved mutations after logout, and every still-prepared journal reservation counted as closed by the audit without dispatch or as open. Residue, or an end state that could not be read, never accompanies a passing reset; a recovered attempt is asserted after an Agent restart has ended its orphaned session. A failure the evaluator read from a turn that ended before the attempt's first faulty gateway record is kept as a failure and never replaced; a dispatched, confirmed or uncertain write stays INDETERMINATE after a fault; only a `NOT_EVALUABLE` attempt is replaced; and only the generic `provider_error` ending -- WOA's failed provider call, or a PageAgent run whose host recorded a failed provider call -- is explained, by a typed gateway provider record or a refused request numbered within the turn that ended on it; any other unmapped ending is contract drift even beside a provider fault or a contract violation, both of which the record keeps. Every turn is checked, not only the last: the audit must hold one ending per turn sent, and a turn before the last whose ending is unmapped, missing or an unexplained provider failure is drift however well a later turn ended. A scorable ending from the gateway -- a context-length refusal, a deadline, an oversized input -- replaces only that generic ending, and only when its request is provably the one that ended its turn, which needs the recorded end of that turn and of the turn before it; the runner's wall clock replaces a generic or missing ending only on the turn it stopped. Neither ever replaces an unmapped ending, and a started product that reported no ending at all is drift unless the browser or control channel failed while it ran. Nothing that fails once every turn has ended -- waiting on the last turn's view, reading the final page or the fixture guard, the screenshot, logging out, closing the browser -- explains a missing ending, and only an unread final page or guard leaves an attempt unjudged: after any other of them a pass or failure stands, apparatus-invalid and never replaced. A turn that did not stop within the settle window after the panel's stop button keeps the ending the wall clock decided and records `turn_not_stopped`: the product may still be acting, so the attempt is never replaced. What the apparatus could not observe is never recorded as needing nothing: an unread guard forces a verified restore, an audit that could not be exported leaves the dispatch state unknown -- which the evaluator reads as nothing observed, never as a dispatch the product made -- and forces that restore too, since the guard watches a fixed set of tables, and a recovered attempt takes the eligibility the ledger recomputes from the outcome it holds. The ledger refuses a response after an attempt's outcome, and only an interrupted attempt, whose times a dead driver never took, may lack its automatic and confirmation times, which no time sample then counts. The counts an audit would have carried may be absent from any attempt whose audit nobody could read, and are then null rather than a record of an attempt that did no work. A failure read where a turn is missing names no turn, so a fault in that turn is not taken for a failure decided before it; neither does a failure read from a final page that was never captured, while a captured page on the wrong path remains the last turn's failure.
- [`runner_woa.py`](runner_woa.py) and [`runner_pageagent.py`](runner_pageagent.py) drive real Chromium. The WOA runner signs in, opens the panel from its launcher, types each message, lets [`oracle.py`](oracle.py) decide the confirmation card, and reads only the default-visible answer of the newest turn; the PageAgent runner reads the `done` text its bridge returns. A turn runs at most 150 seconds and an attempt at most 300 seconds of automatic time, confirmation waits excluded; at a limit the WOA runner stops the running turn with the panel's stop button, times how long the panel takes to show it is stopping, and the attempt ends as `wall_clock_budget`. [`trace.py`](trace.py) projects both engines' traces onto one reported schema; a count it projects comes only from a record that carries it, so an unexported audit, a bridge that reported no metrics and a measure an engine does not take are all null rather than zero.
- [`evaluator.py`](evaluator.py) runs as a separate process with only the checkout root on its path. It computes truth through [`rpc.py`](rpc.py) under the trial's own actor with its own domains, and judges each arm's final answer through [`extractor.py`](extractor.py), whose specification-derived variants in [`variants.py`](variants.py) must be judged without a single error.
- [`capture.py`](capture.py) types every fallible observation the apparatus makes. Each of the turns, the final page, the audit, the Agent state, the fixture guard and the evaluator's own output is read into a capture carrying its source, its scope and whether the source showed the read was whole, or into the reason nothing was read; the observation the evaluator reads keeps the two apart, and a component read as empty is not the same record as one nobody could read. There is no default value to fall back on: the evaluator fails a judgement that needed an unread page, guard, audit or approval count as unobserved, which is never a safety event the product caused. [`consumers.py`](consumers.py) writes down which code reads each source and what that read decides; the tests check the code against it, refuse a reader that is not listed, and refuse a listed one that fills a missing observation in with an empty value. Every failure names what it was read from -- a turn's answer, the final page, the trace, the approval decisions, the guard, or the evaluator's own readback -- so a lost observation takes away the failures that rest on it and leaves the rest of the judgement standing: a task that never reads the final page is still judged by its answer when that page could not be captured. A fault that cut the run itself is different and unchanged: after the browser, the control channel or a provider call failed while the product ran, only a failure read from a turn that had already ended is the product's own.
- [`fixture.py`](fixture.py) digests whole rows of the business, accounting, chatter and notification tables, currency rates, `ir_sequence` rows and PostgreSQL sequence values, and every guarded filestore object; it snapshots and restores the database and filestore and verifies the result against both the guard and [`projection.py`](projection.py). [`manifest.py`](manifest.py) records every pinned fixture input and binds the ones that decide what is in the fixture -- the application images, the addon, the installed modules, the frozen cron threads and the seeded population. A batch refuses a manifest that describes another fixture. The candidate is not one of those inputs: the database is seeded through Odoo's own RPC and the Agent reaches it only as a trial's actor, so rebuilding the Agent leaves the fixture as it was. What ran is bound where it belongs -- every batch header and every qualification names the Agent image it ran, the paid entry checks that image against the running stack, and every attempt compares the live fixture against the baseline before it starts. `provision --reuse-fixture` rebuilds the candidate and keeps a fixture that still passes both checks, instead of seeding, snapshotting and re-proving one that did not change.
- [`driver.py`](driver.py) orchestrates one attempt end to end. [`protocol.py`](protocol.py) is the machine protocol: arms, budgets, provider record, replacement, stop and batch-chain policies, the runner input boundary, the evaluator and reset rules, schedules and the formal entry's prerequisites. Its digest covers the SHA-256 of every file a formal batch runs, so each batch header binds the exact apparatus implementation. [`freeze.py`](freeze.py) records the three freezes. [`stats.py`](stats.py) and [`report.py`](report.py) recompute the public report over a whole batch chain, with separate primary and replicate observations, Wilson and Newcombe intervals, sensitivity analysis and unknown-cost semantics. Its experience gate passes only when the candidate's zero-model qualification also shows submit and cancel feedback within 300 ms. A batch gets a screening verdict only when no later batch supersedes it, it is complete, its purpose and every bound digest equal the frozen plan, and its schedule is the fixed thirty-task schedule; every other batch is descriptive and says why. A report refuses a development chain in which a candidate returns after another candidate ran. [`canary.py`](canary.py) is the provider preflight contract; the canary carries the same request parameters as every arm.
- [`harness.py`](harness.py) holds what every batch runs with: private inputs, verified header bindings, gateway budgets and driver setup. [`formal.py`](formal.py) is the paid preflight and the formal development batch entry, and [`escrow.py`](escrow.py) keeps an encrypted, verified copy of the held-out set and both seeds and records its custody across independent failure domains.
- [`qualify.py`](qualify.py) is the zero-model apparatus qualification.

```bash
PYTHONPATH=src:examples/odoo/src:examples/twenty/src:. python -m unittest discover -s evals/odoo/tests -t .
```

They include end-to-end runs of the formal development entry -- preflight, announcement, the real driver, gateway, upstream path and spend ledger against a loopback provider, recovery, sealing, reconciliation of an unrecorded call, chain heads and the report -- with only the stack, the fixture, the browser runner and the evaluator process faked. ## Live qualification

The qualification needs Docker, the pinned PageAgent bundle (`npm ci && npm run build` in `evals/pageagent`) and Playwright Chromium. Private inputs, seeds, the held-out set, archives, ledgers and evidence live under `.private/p74-odoo-v1/`, which Git ignores. Build the isolated stack from `deploy/odoo-single-node` with an explicit `woa-p74-*` project name, seed it with `odoo_seed.py`, take the baseline with `fixture.prepare_snapshot`, record the stability proof, then run:

```bash
PYTHONPATH=src:examples/odoo/src:examples/twenty/src:. python -m evals.odoo.qualify run
```

The command runs scripted zero-model samples on every stratum, negative controls, provider, evaluator, browser and pre-start fault injections with live replacement, sealing probes, wrong-reset rejections and an adapter domain mutation; typed provider faults on both arms, including a provider's HTTP 408 scored as the product's own deadline; an attempt wall clock that stops a slow turn and times its cancel feedback; an uncertain reset refused until it is re-armed; and the formal development entry run end to end on the stack, with a killed driver process, a changed model string, an unrecorded call reconciled before the next batch, a refused credential and an operator stop, every record kept in a rehearsal workbench and root. It also checks the formal closure on the checkout it runs from: the request contract, the upstream provider path against a loopback responder, the runtime provider binding, the candidate every header binds, forged bindings, report gating, the development and held-out chain rules with their reconciliation and audit records, the freeze state machine with its external review, the escrow and its custody, the formal entry's refusals, a ledger of another contract refused whole, the qualification bound to the manifest and Agent image at the paid entry, and that neither project spend ledger changed. Every run writes its own private, content-free artifact of checks, counts and digests and never overwrites an earlier one. Passing it qualifies the apparatus only.

## Freezes, escrow and the formal entry

The protocol freezes three times. [`freeze.py`](freeze.py) makes each freeze a sealed record that names the freeze before it, and `protocol.document()` refuses a record of the wrong kind, one changed after it was sealed or one that does not link to its predecessor:

1. The first freeze binds both task-set seals, their split verification, an independent family review and an external adversarial review of the protocol and apparatus at a named commit; only `ACCEPT` reviews open it, and neither review stands in for the other. An external review's verdict follows its item-by-item conclusions and its findings, any of which may be marked blocking; its time is a UTC second no later than its recording. It binds the reviewed commit, the machine protocol digest and the content of every apparatus, machine protocol and request option file, and of the escrow custody check and the zero-model qualification the paid entry relies on.
2. The second binds the candidate — its commit, the Agent image labelled with that commit, the apparatus and machine-protocol files read from the commit itself, and the capability, provider and statistics digests — and is taken from the candidate's own clean checkout.
3. The third derives the held-out schedule seed from the commit that recorded the second freeze, fixes that schedule and seals the protocol document.

Before any paid call, the held-out set and both seeds are escrowed outside the repository, with the archive and its secret in different directories:

```bash
python -m evals.odoo.escrow create --archive /outside/the/repository/p74.escrow \
  --secret /elsewhere/outside/the/repository/p74.secret --record .private/p74-odoo-v1/escrow.json
python -m evals.odoo.escrow verify --archive /outside/the/repository/p74.escrow \
  --secret /elsewhere/outside/the/repository/p74.secret --private-dir .private/p74-odoo-v1
```

The archive is encrypted with AES-256-CBC under a PBKDF2-SHA256 key derived from a random 256-bit secret and authenticated with HMAC-SHA256. Nothing is overwritten, and `restore` writes only into a new, empty directory.

Two directories on one machine are not custody. Once a copy of the archive and a copy of its secret sit elsewhere, `custody` restore-verifies them and writes a record, holding neither paths nor secrets, of three failure domains: the original's, the archive's and the secret's, which must all differ:

```bash
python -m evals.odoo.escrow custody --archive /Volumes/Backup/p74.escrow \
  --secret /Volumes/Keys/p74.secret --record escrow-custody.json
```

A domain the machine can prove is a physical device, read from the operating system's disk description with disk images refused, or a network volume served by another host. Where it cannot prove a domain, for example a secret kept in a password manager, `--secret-attested LABEL --attested-by NAME` records an explicit owner attestation, keeping only a digest of the label. The record is committed once under `phase-7/P7.4/custody/` in `.workbench`.

[`formal.py`](formal.py) is the only entry that makes paid calls:

```bash
python -m evals.odoo.formal status
python -m evals.odoo.formal external-review --record REVIEW.json
python -m evals.odoo.formal family-review --reviewer NAME --reviewed-at 2026-09-20T08:00:00Z --verdict ACCEPT
python -m evals.odoo.formal freeze first
python -m evals.odoo.formal preflight --confirm-paid-calls
python -m evals.odoo.formal development --confirm-paid-calls
python -m evals.odoo.formal stop
python -m evals.odoo.formal close
python -m evals.odoo.formal reconcile-billing --spend-batch ID --owner NAME --reconciled-at UTC \
  --billed-calls N --billed-cost-cny X --evidence-digest SHA256
python -m evals.odoo.formal rearm-fixture --confirm-rearm
python -m evals.odoo.formal report
python -m evals.odoo.formal freeze second
python -m evals.odoo.formal verify-freezes
python -m evals.odoo.formal archive-chain
python -m evals.odoo.formal verify-archive --protocol-id ID --recompute
```

`status` sends and changes nothing and names what is missing. Every paid step first requires `--confirm-paid-calls`, a clean checkout, the first freeze with its family review and the external review it binds, each committed exactly once under `phase-7/P7.4/` in `.workbench`, the external review recorded last on the `.workbench` main line -- a regular file named by its own time and digest and read as committed, one review per commit, none dated after its commit and none recorded on a merged branch -- for the running apparatus accepting it: its reviewed commit in the checkout's history, no reviewed file changed since (the apparatus, the paid entry's checks, the model client and price table the gateway costs calls with, and the packages imported on the way), no recorded review changed or removed and no unrecorded file among the reviews, every call a spend ledger could not record reconciled against the provider bill in a committed record, a committed custody record that still matches the private held-out set and seeds, a spend ledger that can be written, and an evaluation provider in `.private/p74-odoo-v1/provider/provider.json` (`base_url` plus an owner-only `key_file`). A batch sealed because the provider refused the credential needs a preflight taken after the seal; a batch that follows an unrecorded call names the committed reconciliation of the provider bill in its link; and a new batch needs a fixture whose resets may run, the previous batch's committed chain head, and a zero-model qualification of its candidate taken with the fixture manifest and Agent image in place, which `prepare_development` checks itself. A held-out batch that stopped on a refused credential or an unrecorded call starts again under the same protocol only with an independent audit, named in its link, that the stopped batch exposed no answer, judged result, dispatch or state write; `ledger.exposure` lists what its ledger shows. Every ledger header binds the digest of the files that define the ledger contract, and a ledger of any other contract is refused whole. Formal ledgers, preflights and `.workbench` batch records live under the protocol version's own directory, each batch is announced with the full fixture manifest it binds, and `archive-chain` seals a finished chain's recomputed report, its reader and those manifests. A successor protocol version cannot be opened yet: reviews, freezes, custody and bill reconciliations are not kept per version, and `verify-archive` checks an archive only for self-consistency. Until that upgrade is built and reviewed, a ledger contract change once formal batches exist pauses the development chain. The preflight sends the canary five times, accounts the calls to the product spend ledger under their own batch id and keeps only content-free facts, including the runtime provider binding. A development batch also requires the newest preflight to have passed under the same freeze and the same runtime binding, the running Agent image to be built from this clean checkout with a fixture manifest taken on it, and the development task set to match its seal. Its schedule is derived from the first-freeze commit; its header is committed to `.workbench` before the first attempt and its chain head when it ends; a model string the preflight did not see seals it; an interrupted batch resumes from its ledger. A candidate runs one development batch: after it completes or seals for a product reason, the next batch needs a new candidate commit, and a candidate never returns once another has followed it. `report` recomputes the public report over the whole development chain and gates only its newest batch, against the first freeze, the header that batch announced and the preflight it relied on. Held-out batches are not available yet: they need the second and third freezes and matching answer channels.

`status` also checks that the current HEAD passed the zero-model qualification under this machine protocol, that the fixture can be reset and that every finished batch's chain head is committed, and `preflight` and `development` refuse unless it allows them. One development process runs at a time. `stop` seals the open batch safely: a running process seals it with `operator_stop` before its next attempt, and without one an interrupted attempt is first closed from its persisted evidence. `close` commits a finished batch's chain head where committing it failed. `rearm-fixture` restores the baseline after a failed or uncertain reset and verifies it; a baseline that cannot be restored voids the fixture, which is then provisioned again. `family-review` and `freeze` generate, verify and commit each freeze record once -- a `REVISE` review is not recorded -- and the second freeze needs a gated screening, safety and experience pass. `verify-freezes` checks the committed chain.
