## 保留与拒绝的优化

保留：

1. `query_entity_records` 支持 `field_ids=[]`，不需要为计数取记录字段。Yudao 和 Odoo 跳过行读取；Odoo 同时避免空字段列表触发全字段读取。
2. 查询直接返回绑定本次查询的精确 `count#1` 聚合证据。模型可直接引用，省掉额外计算和错误引用的修复回合。既有字段、筛选、单位、身份、精确性和证据校验保持有效。
3. 源码查询不再被工具描述强制翻译为英文。原始索引匹配词项，不会自动翻译中文文档；已知代码标识符仍可使用。
4. demo/原封存评测支持 `--executor goal|agent`，复用生产配置，显式区分旧路径和原生工具循环，避免以后只评测旧路径再推广到新路径。

未保留：唯一精确页面匹配后的自动导航结束。单元测试能证明作用条件和新鲜页面核验，但 C 的真实导航通过数由 B 的 7/8 降到 4/8，长尾也恶化。其核心改动和启用配置已撤回。单轮不能证明每个失败都由这项修改引起，仍不足以接受它。

未缩减按意图选择的 schema 分支、字段或范围摘要，未降低推理预算，也未将不确定写入自动重试。初始提示词未显著变小；主要减少的是后续计数数据和调用。

## 架构判断

旧路径 206 次请求、60.6 万输入 tokens，重构路径 350 次请求、493.5 万输入 tokens。问题不是“请求次数越少越好”，而是重复串行决策和越来越大的上下文。B 首轮从模型 egress 到首个 tool_call 的完整响应中位数约 3.71 秒；这不是 TTFT 或线上 UI 的“理解需求”阶段耗时。

下一阶段应以旧目标式解析器的能力和测量结果为基础：先用小上下文声明**全部交付目标**，允许一个请求同时包含业务、源码和页面；确定性解析负责条件、记录与聚合；源码继续用原始仓库检索。仅有一个分类标签会漏掉混合请求，分类失配必须能回退，不能把未检索到变成不存在。每次执行的结果和新页面仍返回同一服务端 Agent。

可并行的是绑定同一账号后的独立元数据/源码读取，或同一输入的独立解释候选；记录身份未解析时的后续读取、依赖前一结果的过滤、导航后的操作、审批和写入仍必须顺序执行。增加廉价声明请求，只有确实减少累计 tokens、串行关键路径和修复次数，才可能更快。当前测试不支持“只增加意图分类调用就一定提速”的结论。

还应先修复具体拒绝信息、任务范围与证据的绑定、计数条件展示及引用投影契约，再评测。缓存要绑定账号、来源版本、上下文和选项，不能缓存实时结果后静默跨权限复用。以上为后续设计方向，尚未实现或资格验证，不冒充本次成果。
